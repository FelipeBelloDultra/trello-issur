Mapa do backend do trello-issur

Referência única de tudo que existe hoje em apps/api: rotas HTTP e seus retornos, eventos de fila, o que é gravado no Valkey e em que formato, e o passo a passo do que acontece internamente em cada operação — como aceitar um convite de workspace. Levantado lendo o código-fonte real, módulo por módulo.

Arquitetura, em uma tela

Domain-Driven Design + Clean Architecture + Ports & Adapters + CQRS, sobre uma regra de dependência estrita: Domain ← Application ← Infra ← Entry points. Cada módulo (account, auth, workspace, notifications) repete essa divisão internamente. Comandos e queries passam por um CommandBus/QueryBus em processo — controllers nunca chamam handler ou repositório diretamente.

Dois processos compartilham o mesmo container de injeção de dependência, mas têm responsabilidades diferentes: index.http.ts serve a API e publica eventos (via outbox); index.queue.ts é quem de fato consome as filas do RabbitMQ e roda o OutboxRelay. Erros seguem três camadas — DomainError lançado no domínio, Either<UseCaseError,T> retornado pelos handlers de aplicação, e HttpException lançada pelo controller a partir do lado esquerdo do Either.

Toda rota abaixo está montada sob o prefixo /api (ex.: POST /api/accounts), exceto as duas rotas administrativas de fila em Infraestrutura → Filas.

Workspace

O módulo mais denso: workspaces, membros (RBAC via account_roles) e convites. Não existe tabela workspace_members — membership e role vivem na mesma linha de account_roles.

Fluxo — Cadastro de conta (+ workspace pessoal)

  1. POST /api/accounts com create_workspace: true → CreateAccountHandler grava a conta e, na mesma transação, duas linhas em outbox_events: account.created e workspace.personal-creation-requested.
  2. OutboxRelay (rodando só no processo queue) faz polling a cada 5s, publica ambos os eventos no RabbitMQ usando o id da própria linha do outbox como chave de idempotência.
  3. AccountCreatedConsumer consome account.created → dispara SendWelcomeEmailCommand (e-mail de boas-vindas via SMTP/Mailpit em dev).
  4. WorkspacePersonalCreationRequestedConsumer consome workspace.personal-creation-requested → dispara CreateWorkspaceCommand({ name: "{primeiro nome} Workspace", isPersonal: true }), criando o workspace pessoal de forma assíncrona (não faz parte da resposta HTTP do cadastro).

Se create_workspace for omitido/false, só o passo 1 (sem o segundo evento) e o passo 3 acontecem — não há workspace pessoal.

Fluxo — Login, refresh e logout

O ponto pouco óbvio deste mecanismo: os JWTs são stateless por definição, mas o sistema consegue invalidá-los antes da expiração (no logout, ou ao rotacionar) porque toda validação faz duas checagens — assinatura/expiração do JWT e um hash espelho gravado no Valkey.

  1. Login — POST /auth/authenticate: compara senha com PasswordHasherGateway.compare contra o hash real (findCredentialsByEmail, único método que não passa por cache); gera par de JWT; grava os dois hashes no Valkey e os dois cookies httpOnly.
  2. Refresh — POST /auth/refresh: lê o cookie, verifica o JWT, confere o hash no Valkey, gera um par novo e sobrescreve as mesmas duas chaves — rotação completa a cada chamada (por isso a rota tem IdempotencyMiddleware de 30s, para um retry de rede não gerar dois pares diferentes).
  3. Logout — POST /auth/logout: verifica o JWT do refresh e apaga as duas chaves do Valkey. Os cookies em si só são limpos no navegador que fez a chamada — qualquer outro lugar que ainda tenha o cookie antigo passa a falhar no passo 2 do AuthMiddleware.

Fluxo — Convite de workspace: criar → aceitar/rejeitar

O fluxo que mais aparece nas dúvidas do dia a dia. As três etapas (criar, aceitar, rejeitar) rodam exatamente o mesmo mecanismo — escrita + evento de outbox na mesma transação Postgres, publicação assíncrona pelo OutboxRelay — só muda o routing key e quem é notificado no fim.

ACriar o convite

  1. POST /workspaces/:id/invites → InviteMemberHandler normaliza o e-mail, checa se já é membro (409 AlreadyAMemberError) e se já existe convite pendente para aquele e-mail no workspace (409 InviteAlreadyPendingError).
  2. Cria WorkspaceInvite com token aleatório de 32 bytes e expiresAt = agora + 7 dias.
  3. Numa única transação (UnitOfWork): grava a linha do invite e uma linha em outbox_events com routing key workspace-invite.created e payload { inviteId }.
  4. OutboxRelay pega essa linha no próximo poll (até 5s de atraso), publica no RabbitMQ com o id da própria linha como chave de idempotência, marca published_at.
  5. WorkspaceInviteCreatedConsumer consome, busca os detalhes do convite; se o e-mail convidado já corresponde a uma conta existente, dispara CreateNotificationCommand (tipo workspace_invite) para essa conta. Se não existir conta ainda, não faz nada — sem notificação, sem retry, sem erro.

BAceitar (ou rejeitar) o convite

  1. PATCH /invites/:token com {action: "accept"} → valida, na ordem: convite existe (404) → está pending (409 se não) → não expirou (410) → o e-mail da conta logada bate com o do convite (403).
  2. Accept, numa única transação: insere o novo membro em account_roles via onConflictDoNothing — se a inserção não afetar nenhuma linha (já era membro, corrida entre duas abas por exemplo), a transação lógica aborta e retorna 409 AlreadyAMemberError, sem marcar o convite como aceito nem gravar evento; se afetar, marca o convite accepted e grava a linha de outbox workspace-invite.accepted com payload { inviteId, accountId }. Tudo atômico.
  3. Reject, também numa única transação (mesmo desenho do accept, sem a etapa de inserir membro): marca o convite rejected e grava a linha de outbox workspace-invite.rejected com payload { inviteId, accountId }.
  4. Publicação e consumo de ambos os eventos seguem o mesmo caminho outbox→relay→consumer da criação; WorkspaceInviteAcceptedConsumer dispara CreateNotificationCommand (tipo workspace_invite_accepted) e WorkspaceInviteRejectedConsumer dispara o mesmo comando (tipo workspace_invite_rejected) — ambos para invitedByAccountId, quem convidou, não quem respondeu.

03Idempotência

Antes de chamar handle(), a base verifica idempotency.<fila>.<chave> no Valkey. Se já existir, dá ack sem reprocessar. Após sucesso, grava a mesma chave com TTL de 24h. Falha do Valkey nessa checagem é fail-open — loga e segue como se não tivesse sido processado ainda (disponibilidade da fila > exactly-once estrito).

Essas duas rotas exigem o header x-internal-token, validado contra a env var QUEUE_ADMIN_TOKEN (segredo operacional por ambiente, não RBAC de produto — mesma categoria de /metrics). Sem o header ou com valor incorreto: 401, sem vazar dados de failed_queue_events.

06Outbox pattern

outbox_events (routing_key, payload jsonb, published_at). OutboxRelay roda só no processo queue, a cada OUTBOX_RELAY_INTERVAL_MS (padrão 5000ms), dentro de um UnitOfWork: busca pendentes com FOR UPDATE SKIP LOCKED, publica cada um com o id da própria linha como chave de idempotência determinística, marca published_at. Se o publish for e o markPublished falhar, o próximo tick republica sob a mesma chave — o consumer absorve a duplicata pela checagem de idempotência.

01Circuit breaker (opossum)

ValkeyClient guarda get/set/del/incr/expire/ttl/keys; DatabaseClient guarda pool.query (o primitivo que o driver do Drizzle chama para toda query). Thresholds via env (CIRCUIT_BREAKER_TIMEOUT_MS=3000, ERROR_THRESHOLD_PERCENTAGE=50, RESET_TIMEOUT_MS=10000, VOLUME_THRESHOLD=10) — conservadores, ainda não calibrados contra tráfego real. RabbitMQ não é coberto (client síncrono, não há o que envolver em timeout/promise) — a resiliência de publish é o próprio outbox.

Débitos e lacunas conhecidas

Encontrados lendo o código nesta varredura — nenhum é bloqueante, mas valem registro.

  • CreateAccountController tem um default: throw new Error() cru no switch de erros — hoje é código morto (só existe 1 erro possível), mas vira um 500 não estruturado se um novo left for adicionado sem atualizar o controller.
  • Sem tempo real para notificações — só GET /notifications via polling, sem WebSocket/SSE nem contagem de não-lidas dedicada.
  • Fluxo de convite tem e2e só para criar → rejeitar — o caminho criar → aceitar ainda não tem e2e dedicado, só specs unitárias com repositórios em memória.

Specs 001–005 do roadmap fecharam o restante do debt pequeno identificado numa varredura anterior (auth das rotas de fila, invalidação de cache RBAC, rejeição de convite, idempotência de replay, permissão de convite) — ver docs/api/specs/ para o histórico de cada uma.

Gerado lendo apps/api/src diretamente (sem inferência) — módulos account/auth/workspace/notifications, filas, cache e schema. Documento de referência, não normativo: quando o código mudar, este mapa fica desatualizado até ser re-varrido.
